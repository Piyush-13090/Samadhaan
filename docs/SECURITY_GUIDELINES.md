# Security guidelines

How to build on Samadhaan without reopening what Prompt 26 closed. Audit:
[`SECURITY_AUDIT.md`](./SECURITY_AUDIT.md). Threats:
[`THREAT_MODEL.md`](./THREAT_MODEL.md).

## 1. API development

- **Closed by default.** `JwtAuthGuard` is global. `@Public()` is a visible,
  reviewed decision. Add `@Roles(...)` for role-gated routes.
- **Validate everything with DTOs.** The global pipe uses `whitelist` and
  `forbidNonWhitelisted`, so unknown fields are rejected.
  - Never accept `role`, `status`, `userId`, `organizationId`,
    `recipientId`, amounts or similar from a body as authority.
  - Bound every string with `@MaxLength` and every number with
    `@Min`/`@Max`.
  - Use enums for sorts and modes.
- **Never interpolate SQL.** Use `Prisma.sql` with bound values. Map sort
  options to constant SQL fragments. `Prisma.raw` only ever takes
  constants.
- **Errors.** Throw `AppException` with a message a user may see. The global
  filter turns anything else into an opaque 500 and logs the detail. Never
  put upstream or library error text in a response.
- **State-changing requests from browsers** must come from an allowed origin
  (`csrfOriginCheck`). Do not add GET routes that change state.
- **Rate-limit** anything expensive (AI, embeddings, exports, uploads,
  search) with `@UserRateLimit`, using tighter limits for costlier work.

## 2. Authorisation patterns

- **Derive access from the session user and the database:**
  - `GovernmentGuard`: office plus jurisdiction predicate;
  - `OrganizationWorkspaceGuard`: membership;
  - `ResolutionAccessService` / `ProjectsService.resolve`: room and project;
  - `KnowledgeAccessService.predicate`: knowledge visibility;
  - `SearchAuthorizationService`: per-entity search policy.
- **Put the rule in the query.** Filter in SQL rather than fetching and then
  hiding. Re-check on the detail read.
- **Answer 404 for "exists but not yours"** so that ids cannot be probed.
- **Separation of duties.** Nobody approves or allocates to an organisation
  they belong to, and nobody adjusts or invites themselves.
- **Background jobs** carry ids only, re-load state, re-check eligibility,
  claim atomically with a lease, and bound their retries.

## 3. Tenant isolation

- **Every new private entity** needs an explicit owner column (organisation,
  project or user) and an access helper.
- **Test both directions** for each new endpoint: organisation A against B,
  office X against Y, and a citizen against both. Cover direct ids **and**
  search, analytics, exports and realtime.
- **Caches of private data** must key on the user or the authorisation scope.

## 4. Files

- **Detect types from content bytes;** never trust the extension, MIME or
  name.
- **Images** are JPEG, PNG or WebP only. Decode with `limitInputPixels`, then
  re-encode before storing (this strips metadata). No SVG.
- **Storage keys** are generated by the server (`buildProblemImageKey` and
  friends) and always checked with `isSafeStorageKey`.
- **Display names** go through `cleanFileName`.
- **Serve private files** only through authorised endpoints, with
  `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and
  `Content-Disposition`.
  - The public media route serves **only** problem-photo keys.
  - A new public prefix needs an explicit allowlist change.
- **Documents for RAG** are bounded in bytes, pages and chunks. Their text is
  untrusted.

## 5. AI security

- **Authorise in NestJS, then build minimal context, then call the AI
  service.** The AI service never queries the database and never decides
  access.
- **Prompt input:**
  - Untrusted text (reports, comments, messages, documents, RAG chunks,
    evidence, organisation descriptions) goes inside a tagged block.
  - Pass it through `neutralise()` and fold newlines for line-based
    sections.
  - Say in the system prompt that it is data, not instructions.
- **Output:** constrained schemas (Pydantic) plus NestJS parsers that check
  enums, ranges, lengths and known references. On failure, fall back safely;
  never pass model text through as a decision.
- **Prompt versions.** Bump the prompt version whenever prompt text
  changes.
- **Keys** live only in the AI service's environment. They are never logged,
  never returned, and never sent to the browser.

## 6. Secrets and configuration

- **Storage.** Secrets live only in the environment or a secret store.
  `.env*` files (except `.env.example`), key files and storage directories
  are git-ignored.
- **Production refuses to start unless:**
  - `AUTH_COOKIE_SECURE=true`;
  - `AI_SERVICE_TOKEN` / `AI_INTERNAL_TOKEN` are set (32+ characters);
  - `JWT_ACCESS_SECRET` is freshly generated (not the placeholder);
  - `CORS_ORIGINS` lists explicit `https` origins;
  - `ALLOW_DEV_SEED=false`.
- **Development conveniences are gated** by `NODE_ENV`: the seed accounts,
  the development AI provider (refused in production), verbose logs,
  OpenAPI docs and localhost CORS.
- **Infrastructure.** Redis needs `requirepass` (`REDIS_PASSWORD`) and the
  database needs TLS, a least-privilege application user, and no public
  exposure. The application user needs DML on application tables plus
  migrations run by a separate deploy role.

## 7. Logging

- **Pino structured logs** with one `requestId` per request. It is validated,
  propagated to the AI service, and returned in error envelopes.
- **Redacted:** `authorization`, `cookie`, `set-cookie`, `x-internal-token`
  and password fields.
- **Never log:** request bodies, prompts, document text, query text or
  tokens. Log identifiers, codes, counts and durations.

## 8. Privacy and data retention

- **Data minimisation:**
  - Public views use allow-list serializers.
  - Location: distances rounded; no coordinates in search results;
    analytics use rounded cells with minimum group sizes.
  - Photos are stripped of EXIF.

**Retention.** Where the period is not yet fixed, it is a product/legal
decision. Nothing is auto-deleted beyond the items below.

| Data | Current behaviour | Policy |
| --- | --- | --- |
| Sessions | Expire after `REFRESH_TTL_SECONDS` (30 days); revoked on logout | Purge revoked or expired rows after 90 days *(future job)* |
| Unattached uploads | Swept after the claim window (about 1 hour) | Implemented |
| Problem photos and reports | Kept with the civic record | Decide on deletion/anonymisation for withdrawn reports *(policy decision)* |
| Notifications | Kept | Proposed 1 year *(policy decision)* |
| Recent searches | At most 10 per user; expire after 30 days idle | Implemented |
| Search and analytics telemetry | Anonymous daily counters, 35 days | Implemented |
| Application logs | Platform-dependent | Proposed 30–90 days, no bodies or PII *(deployment decision)* |
| Audit logs and impact ledger | Append-only, kept | Kept for accountability; erasure only through the maintenance path *(legal review)* |

## 9. Checklist for a new feature

1. Does every route have the right guard, role and rate limit?
2. Is every id resolved against the session user, membership or
   jurisdiction?
3. Are DTOs whitelisted, bounded and enum-typed?
4. Is all SQL parameterised?
5. Is user content rendered as text only?
6. Do uploads get byte detection, a generated key, re-encoding and
   authorised serving?
7. Is AI input delimited and neutralised, and AI output validated?
8. Do caches key on the scope?
9. Is a security regression test included, covering cross-tenant cases?
